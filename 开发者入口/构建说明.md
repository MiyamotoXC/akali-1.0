# 知识库构建说明（开发者入口）

> 本目录（`阿卡莉1.0/开发者入口/`）是**唯一可以写知识库的地方**。
> `通用工具/`（agent 侧）对 `知识库/` **严格只读**（mtime 感知缓存）。
> 所有产物都由本目录的脚本生成，不要手改 `知识库/**/产物/` 与 `知识库/llm/*.json`。

运行方式（在 `阿卡莉1.0` 目录下，用项目 venv）：

```bash
.venv/Scripts/python.exe 开发者入口/build/构建入口.py          # 一键增量构建（推荐）
.venv/Scripts/python.exe 开发者入口/build/构建入口.py --list    # 只看哪些环节需要重建
```

## 0. 一分钟速查：我要做 X → 跑哪个

| 我想做的事 | 命令 |
|---|---|
| 源表（Excel/docx）更新了，重建全部产物 | `build/构建入口.py` |
| 只想看哪些环节过期了 | `build/构建入口.py --list` |
| 强制全部重建 | `build/构建入口.py --full` |
| 只重建角色数据链路 | `build/角色数据构建.py --stage all` |
| 交互式改某个角色的技能/天赋/面板 | `build/角色数据构建.py`（控制台菜单） |
| 只重跑「规则补全」（不调 LLM，幂等） | `build/角色数据构建.py --stage 3` |
| 往「问答补充.txt」加了条目 → 进 QA 向量库 | `build/补充问答录入.py` |
| 同一份条目 → 进小技巧集 tips.json | `build/补充技巧录入.py` |
| 看 tips.json 全量内容（带搜索/筛选） | `build/技巧概览.py` → `调试/tips_总览.html` |

| 打开开发者控制台（查询/改数据/算伤害） | `开发者入口/start.bat`（Streamlit，8501 端口） |

## 2. 一键入口：`build/构建入口.py`

**唯一推荐入口。** 检测输入源变化，按依赖链增量重建，不必手动逐个跑脚本。

用法：

```bash
python build/构建入口.py            # 增量（只重建过期环节）
python build/构建入口.py --full     # 强制全量
python build/构建入口.py --verbose  # 显示每个脚本完整输出
python build/构建入口.py --list     # 只列出各环节状态，不执行
```

依赖链（**顺序不可调换**，后面的吃前面的产物）：

| # | 环节 | 脚本 | 输入 → 产物 | 触发条件 |
|---|---|---|---|---|
| 1 | 角色数据（含 stage 3 规则补全） | `角色数据构建.py --stage all` | 3 个 Excel → raw_data / data.json / talent_* | 任一 Excel 比 raw_data.json 新 |
| 2 | 攻略 docx → md | `攻略转文档.py` | 攻略 docx + 遭遇战历史 docx → 攻略_md/*.md | 任一 docx 比最新 md 新 |
| 3 | 攻略索引 | `攻略索引.py` | 攻略目录 → guide_index.json | docx 比索引新 |
| 4 | Agent 总知识库 | `知识库增量.py` | md + raw_data + talent_* → 拂晓知识库_agent.json | 上述任一比产物新 |
| 5 | 攻略 QA 库 | `攻略问答库构建.py` | 攻略_md → 攻略QA库.json（**调 LLM**） | md 比 QA 库新 |
| 6 | 攻略 QA 向量库 | `问答向量化.py` | QA 库 → 攻略QA向量库.npz（**调 embeddings**） | QA 库比 npz 新 |
| 7 | 小技巧集 | `补充技巧录入.py` | 问答补充.txt → tips.json（**调 LLM**） | 问答补充.txt 比 tips.json 新 |

任一环节失败 → **立即中断后续**（避免用半成品污染下游）。

### 角色数据 stage 内部（`角色数据构建.py --stage all` = 1 + 2 + 3）

| stage | 内容 | 调 LLM |
|---|---|---|
| 1 合表 | 四源 Excel → raw_data.json（面板表为基准，差异化保留）；talent_map / talent_pvp / ·改 天赋补全 | 否 |
| 2 增量 LLM | 新增/解析失败的角色 → data.json 技能结构化 | 是（仅增量） |
| 3 规则补全 | 见 §3.2 `规则补全.py` | **否** |

### 「问答补充」环节

- **`补充问答录入.py`**：`知识库/问答补充.txt` → QA 库（`qa_supp_*` 条目）。触发条件：问答补充.txt 比 QA 库新。
- **`补充技巧录入.py`**：同一份 txt → `知识库/攻略/tips.json`（小技巧集）。触发条件：问答补充.txt 比 tips.json 新。

**顺序要点**：`guide_qa_build` 会**从 md 重建** QA 库，但它会**透传 `qa_supp_*` 条目**（源码内有显式保留逻辑，`--full` 也保留）——所以「先 build 再 append」不会丢条目；不过 append 之后必须让向量库刷新（append 自己会顺带增量嵌入 npz）。

## 3. 链路 A：角色数据（Excel → raw_data.json → data.json）

### 3.1 `build/角色数据构建.py` —— 角色数据主构建 + 交互式控制台

**定位**：把「舰灵数值 / 普攻倍率 / 技能表 / 天赋表」四类源表合并成两份产物：

- `raw_data.json`　—— 以**面板表为基准**合并的原始信息（面板 + 阵营 + skills 原文 + talents）
- `data.json`　　　—— LLM 解析后的**计算表**（技能结构化、buff、CD、恰有字段），agent 侧计算用

用法：

```bash
python build/角色数据构建.py              # 交互式控制台
python build/角色数据构建.py --stage 1    # 只合表（不调 LLM）
python build/角色数据构建.py --stage 2    # 只增量 LLM 解析
python build/角色数据构建.py --stage all  # 合表 + 增量 LLM（构建入口.py 调的就是这个）
```

| 函数 | 作用 |
|---|---|
| `main()` | 命令行入口：解析 `--stage`，决定走控制台还是批处理 |
| `_console_loop()` | 交互式主菜单循环（查询 / 手动更新 / 导入表格） |
| `_run_batch(stage)` | 批处理模式：`1` 合表、`2` 增量 LLM、`all` 两者 |
| `_resolve_path(p)` | 相对路径 → 基于脚本目录的绝对路径（`.env` 与默认值里的相对路径用） |
| `scan_knowledge_base(dir)` | 扫描知识库，按文件名关键词识别三类源表（含「舰灵数值」/「普攻倍率」/「CharSkillInfoLv10 或 技能」） |
| `_extract_and_normalize()` | 扫描 + 提取四源数据 + **舰名归一化** → `(panel_by_key, normal_by_key, skill_by_key, talent_by_key, talent_map)` |
| `_merge_to_raw(...)` | 以面板表为基准合并四源 → `raw_data.json`（**差异化更新**：角色集合严格等于面板表，多余角色 prune） |
| `_merge_tables()` | `_merge_to_raw` 的免 LLM 入口，返回面板表舰名列表 |
| `_fill_kai_talents()` | **·改 角色天赋补全**：改造前后天赋一致，从原型舰复制。基座规则 = `_KAI_BASE` 显式映射 → 同名/唯一同名含括号角色；**多候选且无映射时不猜**，记入待办 |
| `_generate_talent_pvp()` | 从**源表** `底层数据/源文件/天赋表pvp*.xlsx` 生成 `talent_pvp.json`（读源表→写产物）。**同一个格子若同时写了本体与改造名（如 `雪风/祥瑞御免-丹阳`）→ 格内每个能解析出的正规名都登记同一编码**（改造前后推荐一致）；**一个格给了多套点法（如 `1211/1221`）→ 取第一种**（计算时按表格给出的第一套来） |
| `_load_skill_overrides()` | 读 `源文件/skill_text_overrides.json`（`{舰名: {技能字段: 文案}}`）：源表尚未同步、但已人工确认的新版技能文案；`_merge_to_raw` 合表后**最后应用**，不会被源表覆盖 |
| `_clean_skill_value(v)` | 技能字段清洗：空串 / `???` / 纯空白 → 视为无（从 dict 删除该 key） |
| `_incremental_llm(only_names, force)` | **增量 LLM 解析技能** → 更新 data.json。`only_names` 非空时只解析这些角色（按 `match_key` 定位正规名），`force` 被忽略 |
| `_skills_empty(ship)` | 判断角色技能是否全空（上次解析失败留下的空壳 → 需重解析） |
| `import_tables()` | 控制台「导入表格」：合并 raw_data.json + 自动增量 LLM 补全 data.json |
| `_menu_query()` | 菜单：查询角色底层信息 + 计算表摘要 |
| `_menu_update()` | 菜单：手动改技能描述/天赋 → 存底层 → 重解析该角色 → 更新计算表 |
| `_menu_import()` | 菜单：导入表格（合并 + 增量 LLM） |
| `_edit_panel()` | 交互式编辑基础信息（舰名/舰种/所属/稀有/装填/装甲类型 + 面板十项）；输入编号→新值；**留空=保留原值**，`q` 结束 |
| `_edit_talents()` | 交互式编辑天赋（四行二列 1A/1B~4A/4B），格式 `天赋名：效果`；**留空=保留**，输入 `-` = 清除 |
| `build_combatdata(...)` | 三源数据合成一个 `CombatData` 对象（面板 + 普攻 + 技能） |
| `_extract_ramp_buffs(text)` | 从技能描述提「每 X 秒 +Y%，最多 +Z%」**递增光环** → `ramp_buffs`（仅支持封顶型） |
| `_check_suspicious_names(names)` | 近似舰名告警，提示可能需要补 `config/ship_name_map.json` |
| `_levenshtein(a, b)` | 编辑距离（近似舰名判定用） |
| `norm(s)` / `_norm(s)` | 内部舰名归一化辅助（去间隔号/空白/括号、转小写） |

### 3.2 `build/规则补全.py` —— stage 3 · 规则补全（原 `patch.py` 的 11 个补丁已收编）

> 2026-09-15 起补丁性质的工具**已删除**：原先这些逻辑是 `patch.py` 的 11 个一次性子命令，
> 每次重建后要**手动挑着跑**，漏跑就出现 agent 侧字段缺失。现在统一收进完整流程：
> `角色数据构建.py --stage all`（= 构建入口.py 第 1 步）在合表 + 增量 LLM 之后**自动执行** `run()`。
> 单独重跑：`角色数据构建.py --stage 3`（不调 LLM、全部幂等，重复执行结果逐字节不变）。

| 函数 | 对应原 patch 子命令 | 作用 |
|---|---|---|
| `step_newlines(raw, log)` | `newline_fix` | 把产物里技能文本的**字面 `\n`**（反斜杠+n）转真实换行；覆盖 raw_data.json 与 custom_ship_config.json |
| `step_speed(raw, data, log)` | `speed` | 航速对齐：`raw.panel.面板.航速`（stage 1 从源表带出）→ `data.speed` |
| `step_buffs_normalize(data, log)` | `buffs_reset` | **常驻 buffs 恢复引擎默认**（全伤害增加/减免 0.2），清 LLM 误归进常驻的持续 buff/旗舰光环/幻觉值 |
| `step_skill_buffs(raw, data, log)` | `skill_buffs` | `skill_buffs / flagship_buffs / raguz_bonus / cd_effects` 代码规则提取（**非空覆盖**，覆盖 LLM 输出） |
| `step_ramp(raw, data, log)` | `ramp` | 递增光环 `ramp_buffs`（「每X秒+Y%，最多+Z%」）+ 对应常驻键清零（复用 `main._extract_ramp_buffs`，防两套正则漂移） |
| `step_skill_cd(raw, data, log)` | `skill_cd` | 技能循环 CD 回填：原文「每 X 秒+动词」而 `cd=0` 的技能（**已有 CD 不覆盖**） |
| `step_alwayscrit(raw, data, log)` | `alwayscrit` | `always_crit` 必定暴击标记置位；未命中清残留（幂等） |
| `step_condextra(raw, data, log)` | `condextra` | 条件增伤 `static_buffs` 置位；未命中清残留（幂等） |
| `step_ignite(raw, data, log)` | `ignite` | 点燃 part 补全：仅当该技能桶**还没有**点燃段（规则提取，LLM 兜底） |
| `step_normal_baseline(data, write_slot, log)` | `normal` | **普攻基准比对**（基准 = 数值自动化表「普攻列表」）：自动补齐 `slot`/`weapon_code` 元数据（**不碰倍率/hit/CD**），全量比对报告写 `调试/普攻基准识别报告.txt` |
| `_extract_ignite(desc)` | — | 点燃配置提取（每跳伤害/持续/概率/次数/CD）；无点燃返回 None |
| `_baseline_for(baseline, name)` | — | 取普攻基准段：先按原名，`·改` 后缀回退原型舰（改造前后普攻同源） |
| `_preset_of(weapon_type)` | — | `weapon_type` → `preset_damage_type` |
| `_label_to_weapon_ammo(label)` | — | 克制表弹种标签 → `(weapon_type, ammo_type)`，如 `驱逐通常`→`(驱逐炮, 通常)` |
| `_fix_literal_newlines(obj)` | — | 递归转换容器内字符串的字面换行 |
| `_load / _save` | — | 读写产物 JSON（写前自动备份 `.bak-post-时间戳`） |
| `run(verbose)` | — | **主入口**：一次读写 raw/data，按上表顺序执行全部步骤；任何一步抛错则**不落盘** |

**两条删除理由（写下来防止回退）**：

1. 这些全是「描述文本 → 结构化字段」的**确定性代码规则**，本就该在每次构建时自动重算，而不是靠人记得去跑补丁；
2. `normal --write fix`（全量同步普攻数值）这类危险操作已废弃——stage 1 的普攻本就取自源表，两表口径差异只在报告里列出供人工核对。

> 天赋（`talents` / `talent_map.json` / `·改` 复制）由 **stage 1** 的 `_merge_to_raw` + `_fill_kai_talents` 负责，不在 stage 3 重复。

### 3.3 `build/标准化副本.py` —— 标准化副本生成

单一 `main()`。流程：

1. 读 `raw_data.json`（原始面板 + 阵营名国籍 + talents）
2. 读现有 `data.json`（技能/buff 标准化产物）
3. **面板数值调整**（`PANEL_RATIO`）：航空 ×1.17、装甲 ×1.17、雷击 ×1.10、血量 ×1.10、对空 ×1.10、命中 ×1.10、幸运 ×1.05
4. 按 `PANEL_ATK_MAP` / `PANEL_DEF_MAP` 把面板字段拆进 `attack_panel` / `defense_panel`
5. 合并 `talent_pvp.json` 作为 PVP 推荐天赋

> ⚠ 比例调整的口径在 `PANEL_RATIO` 一处，改口径只改这里。

## 4. 链路 B：攻略（docx/md → 索引 / 总知识库 / QA 库 / 向量库 / tips）

### 4.1 `攻略转文档.py` —— 攻略 docx → md

| 函数 | 作用 |
|---|---|
| `docx_to_md(path)` | docx → markdown 文本（标题/表格转换、图片省略、段落保留） |

### 4.2 `攻略索引.py` —— 攻略索引

扫描 `知识库/攻略/**` 生成 `guide_index.json`（`{updated, guides:[{id,title,tags,path,kind,desc,category}]}`）。

| 函数 | 作用 |
|---|---|
| `main()` | 全量重建索引；**保留已人工维护的 tags/desc**（按 path 合并，不覆盖）；同时调用 `_merge_file_paths` 把 path 写回精简版 JSON |
| `_clean_title(fn)` | 从文件名提干净标题：去扩展名、去数字前缀、去版本号尾 |
| `_category_for(...)` | 分类判定：萌新入坑 / 一图速查 / 练级须知 / 进阶必备（按文件夹 7/8/9 或标题关键词） |

### 4.3 `知识库增量.py` —— Agent 总知识库

产物 `知识库/llm/拂晓知识库_agent.json`，供 agent `kb_search`。**三级增量**：文件 MD5 → 章节 MD5 → chunk ID。

处理管线：`clean_text` → `detect_sections` → `split_text_into_chunks` → `extract_keywords` / `detect_topic` → `assemble_and_write`

| 函数 | 作用 |
|---|---|
| `strip_images(t)` | 去掉 markdown 图片语法 |
| `strip_md_artifacts(t)` | 去表格分隔行、去掉表格竖线、链接转纯文本 |
| `clean_text(t)` | 清洗总入口（上述两 + 折叠多余空行） |
| `split_text_into_chunks(t, max_len=1000, min_len=450)` | 按长度切 chunk |
| `detect_sections(lines, source)` | 识别章节（供章节级增量与 chunk ID 用） |
| `extract_keywords(text, section, topic, source, max_k)` | 抽检索关键词 |
| `detect_topic(default_topic, section_title, text)` | 判定 topic（按 `GAME_TERM_DICT` 等） |
| `file_hash(p)` / `text_hash(t)` | 文件级 / 章节级 MD5（**增量判定的依据**） |
| `make_file_prefix(source)` / `make_chunk_id(...)` | 稳定 chunk ID：`{file_prefix}_{section_hash[:8]}_{seq}` |
| `process_markdown_file(...)` | 处理单个 md → `(chunks, section_hashes)` |
| `load_existing_kb()` | 读现有产物（不存在返回 None） |
| `build_file_hash_map(existing)` | 从旧 metadata 提文件级 hash |
| `build_section_hash_index(existing)` | 构造 `(source_file, section_hash) → [旧 chunk]` |
| `incremental_update(...)` | **主增量函数**：`force_full=True` 时忽略旧产物全量重建 |
| `assemble_and_write(...)` | 组装最终 JSON 并落盘 |

> 另有 `IMAGE_CHUNKS`（把图片类教程手工写成文本 chunk 塞进总库）与 `NON_MD_SOURCES`（非 md 来源集合，用于增量判定排除）。

### 4.4 `攻略问答库构建.py` —— 攻略 QA 库

从 `攻略_md/` 全量正文切 chunk（**复用 `kb_incremental` 的清洗/分节/切分**），每个 chunk 由 LLM 生成一条玩家视角问法，输出 `攻略QA库.json`（405 条量级）。

| 函数 | 作用 |
|---|---|
| `main()` | 增量构建：文件 MD5 未变 → 整文件沿用旧 QA（不调 LLM）；chunk 未变（ID 含 section hash）→ 沿用旧问题 |
| `_gen_question(chunk)` | 调 LLM 为单个 chunk 生成问题；失败返回 `''`（嵌入时退化为纯正文） |

两条**必须知道的**逻辑：

- `_EXCLUDE_MD = {"2 游戏简介.md"}`：该 md **不进攻略 QA 库**（避免「游戏简介」类问题被路由到攻略线），但总知识库仍保留。
- **`qa_supp_*` 透传**：`补充问答录入.py` 写入的条目在此**从旧 JSON 透传保留**（`--full` 也保留），不会因为重建而丢失。**修订这些条目要重跑 append 脚本，不是重跑本脚本。**

### 4.5 `问答变体生成.py` —— 口语问法增强

| 函数 | 作用 |
|---|---|
| `main()` | 为每个 chunk 生成 2~3 条玩家口语变体存进 `alt_questions`（`--limit N` 调试、`--full` 全部重生成） |
| `_gen_variants(chunk)` | 调 LLM 生成口语问法；失败返回 `[]` |

**为什么存在**（2026-09-07 诊断）：库内 question 是书面问句，自测 hit@1 98~100%，但**真实口语集仅 81%** —— 存在语义鸿沟。变体行由 `问答向量化.py` 作为**独立向量行**（`ids` 指回同一 chunk，检索时按 `_VARIANT_DISCOUNT` 打折）。

### 4.6 `问答向量化.py` —— QA 向量库

| 函数 | 作用 |
|---|---|
| `_embed_texts(texts)` | 批量嵌入（带 429 重试），按输入顺序返回 `np.float32` 矩阵 |
| `main()` | 增量嵌入：以**嵌入文本 MD5** 为键复用旧向量，仅新增/变更 chunk 调 API；换模型（维度变化）→ 全量重建；产物 `攻略QA向量库.npz`（`ids` / `hashes` / `matrix`，已 L2 归一化） |

嵌入文本 = `question + "\n" + content`；`EMBED_MODEL` 默认 `text-embedding-v4`（可用环境变量覆盖）。

### 4.7 `补充问答录入.py` —— 问答补充 → QA 库

| 函数 | 作用 |
|---|---|
| `main()` | 解析 txt → LLM 生成 question/alt_questions/keywords → 追加进 QA 库（`qa_supp_NNN`，**按 id 幂等**）→ 增量嵌入 npz |
| `_gen(item)` | 为单条常识生成 `(question, alt_questions, keywords)`；失败退化为纯正文 |
| `_embed(texts, client)` | 批量嵌入（带 429 重试） |
| `_build_texts_and_ids(chunks)` | 构造嵌入文本与 `ids`（每 chunk 一行 `question+content`，每个 alt 变体再一行） |

### 4.8 `补充技巧录入.py` —— 问答补充 → 小技巧集

| 函数 | 作用 |
|---|---|
| `main()` | 解析 txt → LLM 只生成 `title/category/tags` → 按 **content 原文**去重追加 → 备份并写回 `tips.json` |
| `_gen(item)` | 为单条常识生成 `(title, category, tags)`；失败退化标题=正文前 12 字 |
| `_norm_content(s)` | 内容归一（去空白与标点）用于去重比对 |

**两条设计原则**：

- **content 保持原文逐字**：既防编造，又让重跑**幂等**（按内容去重即可跳过已入库条目）。
- 分类提示词带**释义表**（`_CAT_DESC`）；新增了第 12 类 **「系统与界面」**（港区/设置/UI 操作）。

## 7. 数据契约与坑（改之前先看这里）

1. **`raw_data.json` 与 `data.json` 的分工**：前者是「以面板表为基准的原始信息」，后者是「LLM 解析后的计算表」。**改技能文本改 raw（或控制台），改结构化结果改 data。**
2. **角色集合以面板表为准**：`DataStore.prune` / `RawDataStore.prune` 会删掉不在面板表里的角色。
3. **`match_key` 保留舰船编号括号**（`(DD-459)`），否则大小拉菲会被合并。
4. **天赋**：`·改` 角色从原型舰复制；多候选且无 `_KAI_BASE` 映射时**不猜**。天赋名须与 agent 侧 `talent_map.json` 逐字一致。
5. **`xlsx_std.py` 不是多余**：openpyxl 解析 `数值自动化表.xlsx` 会崩。
6. **`skill_buff_extractor` 的实际逻辑在 `通用工具/core/`**，`build/src/` 里只是薄封装。
7. **`qa_supp_*` 与 `tips.json` 的 `t130+`** 由两个 `append_*` 脚本负责，**重跑主构建不会覆盖它们**（QA 库有透传逻辑；tips.json 不在主链上）。
8. **LLM 相关环节**（技能解析 / QA 问题 / 口语变体 / append 两个脚本）都会消耗额度；三者都做了「MD5 不变就跳过」的增量。
9. **prompts.py 是业务规则唯一集中地**：技能分段、hit 计数规则等，改解析口径先改这里。
10. **规则类字段不许再手补**：点燃 / 持续 buff / 航速 / CD / 递增光环 / 必定暴击 / 条件增伤 / buffs 归一 / 换行 全部由 **stage 3（`规则补全.py`）自动产出**，原 `patch.py` 已删除——发现某字段缺失，先查 `角色数据构建.py --stage 3` 的输出，不要新造补丁脚本。
11. **产物必须跨进程稳定**：`通用工具/core/skill_buff_extractor.py` 解析 scope 时遍历的 `ref.nations / ship_types / names` 是 **set**，直接遍历顺序随机（哈希随机化）——已全部改为**排序遍历**，且 aura 的 scope 去重后按 `(kind, value, op)` 排序。新增提取逻辑同理：**凡进产物的列表一律确定顺序**，否则 stage 3 每次跑都会「有变化」、幂等性报废。
